# Cloud Intelligence ローカル Home Assistant 統合

[English](README.md) | [简体中文](README.zh-CN.md) | [日本語](README.ja.md)

**ローカル統合のベータ版です。** 非公式の独立した
コミュニティプロジェクトで、最初の対応機種は Wilo HiMulti-1 WiFi のみです。
Android の Cloud Intelligence（云智能）で取得した、ご自身の機器の LAN 認証情報を
インポートします。アカウントログインやクラウド機器検索ではありません。Google ログイン、
認証情報の抽出、自動更新は実装していません。アプリにエクスポート機能があるとは限りません。

## 機能とインストール

- Wilo のネイティブ機器と12個の読み取り専用状態：水圧、水温、目標圧力、モード、
  故障コード、故障、電源許可、モーター運転、始動圧力比、ソフトウェア版、目標/実際の回転数。
- 機器ごとに標準 HA 設定エントリーを作成し、複数機器、認証情報の保存、再起動後の復元、
  再インポート、アドレスの再設定に対応します。運転制御エンティティやサービスはありません。
- 更新は標準120秒、最短60秒。各通信の総予算は10秒で、12個の実際の状態を受信すると直ちに終了。
  常時起動アプリ、クラウド接続、非公開ヘルパー、常駐リスナーは使用しません。
- HA 2026.9.1 / Python 3.14.6 で検証済みです。オフラインのライフサイクルテストは合成通信を使い、
  別途、実機で初回設定、12個の状態、自動ポーリング、HA プロセスの完全再起動を確認しました。
  再起動後も同じ設定エントリーと機器・エンティティ ID が保持され、認証情報を再入力せず新しい状態を受信しました。
- 短期間の観察中に一度読み取りが失敗しましたが、次の自動ポーリングで回復しました。
  長期無人運用、ブラウザーの表示確認、他機種は引き続き検証対象です。

コードの `custom_components/cloud_intelligence` 全体（`_core`、`translations` を含む）を
HA 設定ディレクトリの `custom_components` 内にコピーして再起動します。
**設定 → デバイスとサービス → 統合を追加 → Cloud Intelligence (Local)** で次を入力してください。

| 項目 | 内容 |
| --- | --- |
| Name | 表示名。既定は Wilo HiMulti-1 WiFi |
| Host | HA から到達できる機器のプライベート LAN IPv4。公開 IP や DNS 名は不可 |
| `productKey` | 対応キーは `a15zaTr5sp1` のみ |
| `deviceName` | 認証情報内の固定 ALCS 識別子。表示名ではありません |
| `accessKey`、`accessToken` | ご自身の機器のローカル認証情報。機密情報です |

`iotId` やクラウドパスワードは不要です。機器の UDP 5683 との双方向通信が必要で、
マルチキャスト検索はしません。初回追加には機器の識別、認証、12状態の検証が必要です。
ACK や更新要求のエコーだけでは成功になりません。各回に固定の `refresh=1` 状態レポート要求を
一度だけ送信します。電源・モード・圧力設定は変えませんが、純粋な GET や受動監視ではありません。
未対応機種への能動的なレポート要求は拒否し、TSL の書き込み属性から制御を有効にしません。

### HACS でのインストール

HACS の **カスタムリポジトリ** で
`https://github.com/xiaoyaner-home/ha-cloud-intelligence` を **Integration** として追加し、
ダウンロード後に HA を再起動してください。その後 **Cloud Intelligence (Local)** を追加します。
カスタムリポジトリとして提供するベータ版であり、HACS 標準カタログには掲載されていません。

手動インストール用 ZIP は [GitHub Releases](https://github.com/xiaoyaner-home/ha-cloud-intelligence/releases)
から取得できます。内容は `custom_components/cloud_intelligence/...` なので、HA 設定ディレクトリに
展開して `custom_components/cloud_intelligence/manifest.json` が存在する状態にしてください。
HACS はリポジトリのソースを使用し、この手動 ZIP は使用しません。
リポジトリ直下の `cloud_intelligence` パッケージはコピーしないでください。

## 安定エンドポイント候補（実機未検証）

同一クライアントは最初に OS が割り当てた認証/Observe 用 UDP 送信元ポートを記憶し、成功・失敗・
タイムアウト・キャンセル後も再バインドします。毎回、独立した一時ソケットで機器を厳密に識別した後、
認証・購読・固定レポート要求を一度行い、全ソケットを閉じます。同一クライアントの並行読み取りは
待機せず直ちに失敗し、受け付けた読み取りの総予算は従来どおり10秒です。ポート競合時は明示的に失敗し、
別ポートへの切り替えや追加再試行はしません。ポート設定、共有ソケット、再利用オプション、常駐リスナー、
ハートビートは追加しません。通信間にポートは予約されず、設定・診断・repr に保存・表示しません。
新しいクライアントやプロセスは別のポートを選択できます。

このベータ変更は、単一変数の長期比較のためにエンドポイントの変動だけを減らす候補です。
上記の既存実機記録は本候補の検証結果ではありません。ローカルの close は遠隔セッションや監視登録の
解除を意味せず、同一エンドポイントでの再認証も清掃・復旧を保証しません。Observe=1/RST による解除や
機器障害の根本修正は主張しません。公開前に独立レビューと限定的な実機長期検証が必要です。

## 保護・復旧・制限

認証情報は HA の標準設定エントリーに保存され、**本統合では暗号化しません**。HA の設定、
バックアップ、アクセス権を保護し、認証情報、機器識別子、アドレス、パケットを Issue に貼らないでください。
保存しても有効期限は延長されません。認証が無効になったら HA の再認証から、同じ `productKey` と
`deviceName` の認証情報を再インポートします。別の機器は拒否されます。アドレス変更にはエントリーの
**再設定** を使用し、認証情報も再入力してください。更新間隔はオプションで変更できます。

初回の接続失敗は HA 標準の再試行、更新失敗は利用不可になります。後続の部分レポートで欠けた状態は
不明となり、ゼロや以前の値で補いません。電源許可とモーター運転、LAN 到達性とクラウド接続は別です。
`locally_received_at` は HA ホストの実際の受信時刻で、機器のタイムスタンプではありません。
対応する ALCS opt 1 はパケット MAC やリプレイ保護を提供しないため、信頼できる LAN のみで使用してください。

長期運用、ファームウェア差異、認証情報の失効、ブラウザー表示は引き続き検証が必要です。
完全なアカウント検索、Google ログイン、自動更新、他機種、運転制御は本候補版の範囲外です。
基本 UI は en、zh-Hans、zh-Hant、ja と英語へのフォールバックを備えますが、全言語対応ではありません。

開発用の[固定依存](requirements-dev.txt)をインストール後、`make check` で純 Python コアと
実際の HA 2026.9.1 コンテナーのオフラインテスト（2 GiB / 2 CPU）を実行します。
個別実行は `make check-core` / `make check-ha`。詳細は[英語版](README.md)、
[要件](docs/requirements.md)、[検証](docs/verification.md)、[セキュリティ](SECURITY.md)を参照。
